# SalaryClock macOS 메뉴바 앱 설계 문서

작성일: 2026-09-22

## 1. 개요

SalaryClock을 macOS 메뉴바 앱으로 옮긴다. 종일 띄워놓고 금액이 쌓이는 걸
곁눈으로 보는 게 목적이므로, **금액을 메뉴바에 직접 텍스트로 띄우고**
클릭하면 시계와 상세가 담긴 팝오버가 떨어진다.

```
메뉴바  …  ◔ ₩83,412  ▸  🔋 100%  화 오후 1:24
                  │
         클릭 ───▸ ╭────────────────╮
                  │      ◐ 🙈 ⚙ ⏻  │
                  │    ╱ 12  ╲      │
                  │   9   ┼   3    │
                  │    ╲  6  ╱      │
                  │                 │
                  │  ₩83,412.4      │
                  │  +5.8 / 초      │
                  │  퇴근까지 04:00:00│
                  ╰────────────────╯
```

네이티브 Swift로 만든다. 웹앱은 그대로 두고, 두 앱이 `shared/golden/`의
기대값 파일을 공유해 계산 규칙과 디자인 토큰이 갈라지지 않게 한다.

## 2. 범위

### 포함

- 메뉴바 타이틀에 적립 금액 표시 (갱신 주기는 사용자 설정, 기본 1초마다 정수 갱신 — 4.2)
- 클릭 시 팝오버: 시계 1종, 금액, 초당 적립액, 퇴근까지 남은 시간, 테마·가리기 토글 (4.3)
- 설정 창: 급여, 근무시간, 점심, 실수령액 기준(공제율 직접 입력 포함), 근무일수(자동/달력/직접 입력),
  로그인 시 자동 실행, 메뉴바 갱신 주기 (4.4)
- 웹과 공유하는 도메인 규칙 변경 (휴무일, 자정 초기화)
- 두 구현의 일치를 검증하는 골든 파일

### 제외 (YAGNI)

- Windows 지원 — 윈도우 트레이는 아이콘만 달 수 있고 글자를 못 넣는다.
  이 앱의 주 화면이 성립하지 않으므로 다른 설계가 필요하고, 그건 별도 과제다
- 시계 얼굴 10종 — 팝오버가 작아 차이가 드러나지 않는다. `minimal` 1종만 옮긴다
- 코드 서명, 공증, 배포 — 본인 기계에서 빌드해 쓴다 (10장)

**제외한 건 기능이지 디자인이 아니다.** 옮기는 화면은 웹과 같아 보여야
한다. 색·글꼴·도형 수치를 눈대중으로 맞추지 않고 값으로 옮긴다 (5장).

### 뒤집힌 제외 항목

실행 중 사용자가 직접 요청해 아래 세 가지가 제외에서 포함으로 뒤집혔다 —
원래 이 장에 있던 문구는 지웠고, 실제로 들어간 자리는 각 절에 있다.

- **달력으로 근무일 지정** (`workDaysMode: 'calendar' | 'manual'`) — 같은
  설정인데 웹과 맥이 다른 금액을 보여준 사고(근무일수가 맥에서 통째로
  빠져 있었다)를 겪은 뒤 요청이 들어왔다. 근무일수를 전부(자동/달력/직접
  입력) 넣기로 했다 (4.4)
- **공제율 직접 입력** — 같은 요청에 함께 들어갔다 (4.4)
- **다크모드 토글** — 웹과 같은 규칙을 그대로 가져온다. 설정 창이 아니라
  팝오버에 있다 (4.3)

**가리기 토글**은 애초에 이 장에 명시된 적이 없었지만(웹에는 있었다),
다크모드 토글과 같은 시점에 팝오버에 들어갔다 (4.3).

### 결정을 되돌린 것

이슈 #1은 Tauri v2 + GitHub Actions 빌드로 결정돼 있었다. 그 결정은
**(1) 개발 기계가 Windows 11이고 (2) Windows도 타깃**이라는 두 전제에서
나왔는데, 작업 기계가 Xcode가 깔린 맥으로 바뀌었고 Windows는 범위에서
빠졌다. 전제가 모두 사라졌으므로 네이티브로 되돌린다.

Tauri를 유지하면 메뉴바 숫자를 1초마다 갱신하기 위해 웹뷰를 상주시켜야
하는데, macOS가 가려진 `WKWebView`의 타이머를 스로틀할 수 있어 이 앱의
핵심인 "숫자가 흐르는 것"이 보장되지 않는다. 우회하려면 Rust가 타이머를
쥐고 웹뷰는 계획만 넘기는 구조가 되는데, 그러면 숫자를 찍으려고 웹뷰를
상주시키는 꼴이 된다.

대가는 **도메인 규칙이 두 벌이 되는 것** 하나이고, 9장의 골든 파일로
관리한다.

## 3. 도메인 규칙 변경 (웹·맥 공통)

`lib/` 아래에서 고치고 웹앱에도 그대로 반영한다. 규칙의 단일 출처는
계속 `lib/`다.

### 3.1 시프트 선택

`resolveShift`를 세 단계로 다시 쓴다.

```
1. now를 포함하는 시프트가 있으면        → 그것        (working / lunch)
2. 없고, 오늘 안에 끝난 시프트가 있으면  → 그것        (after — 총액 유지)
   단, 오늘 출근할 시프트가 더 가까우면 그쪽         (before — 0원)
3. 그 외                                  → 오늘 시작할 시프트 (before — 0원)
```

지금은 "시간적으로 가장 가까운 시프트"를 고른다. 그 규칙은 퇴근 직후
적립액이 0으로 리셋되는 걸 막으려고 넣은 것인데, 자정을 넘긴 뒤에도
어제 시프트가 계속 가장 가까워서 **어제 총액이 그대로 남는 버그**가 있다.

"오늘 안에 끝났는가"로 바꾸면 자정을 특별 취급하지 않고도 초기화가
저절로 나온다.

| 상황 | 지금 | 바뀐 뒤 |
|---|---|---|
| 09–18 근무, 20:00 | 오늘 총액 | 오늘 총액 (2단계) |
| 09–18 근무, 00:30 | **어제 총액** (버그) | ₩0 (3단계) |
| 09–18 근무, 08:00 | ₩0 | ₩0 (3단계) |
| 22–06 야근, 00:30 | 적립 중 | 적립 중 (1단계) |
| 22–06 야근, 07:00 | 방금 끝난 총액 | 방금 끝난 총액 (2단계) |
| 22–06 야근, 21:00 | 어제 총액 | ₩0 · `출근까지 01:00:00` (2단계의 근접성 단서) |

2단계의 단서(`단, 오늘 출근할 시프트가 더 가까우면`)는 나중에 붙었다.
처음 표에는 야간근무의 출근 전 구간이 없었고, 그래서 어제 시프트가
오늘 06:00에 끝나는 야간근무에서는 21:59까지 2단계가 계속 걸려 `before`가
아예 나오지 않는 버그를 이 표가 못 잡았다. 근접성은 2단계 안에서만 쓴다 —
예전의 "가장 가까운 시프트" 규칙으로 되돌리면 00:30에 어제 퇴근이 오늘
출근보다 가까워져 자정 초기화가 다시 깨진다. 어제 퇴근은 오늘 자정보다
앞이라 애초에 2단계 후보가 아니므로, 두 규칙이 서로를 깨지 않는다.
거리가 같으면 끝난 쪽을 남긴다.

야간근무는 이 앱의 설계 동인이 아니다. 다만 설정 화면이 22:00–06:00
입력을 여전히 허용하므로, 지원하는 설정이 조용히 깨지게 두지 않는다.
"자정에 리셋"이라고 직접 쓰면 더 짧지만 야근 중에 0이 된다. 위 규칙은
몇 줄 더 쓰는 대신 둘 다 맞는다.

### 3.2 휴무일

지금 `salary.ts`는 요일을 전혀 보지 않아 **토요일에도 돈이 쌓인다.**
판정 재료는 `lib/calendar.ts`에 이미 있다.

```ts
/** 그 날이 쉬는 날인가 — 주말·공휴일에 overrides를 반영한 결과 */
export function isDayOff(overrides: readonly string[], dateMs: number): boolean
```

`dayOverrides`는 **`workDaysMode`와 무관하게 반영한다.** 달력에서 "이날은
쉰다"고 찍은 건 근무일수를 어떤 방식으로 세는지와 별개로 참인 사실이다.

**판정 대상은 `now`가 아니라 시프트의 시작일이다.** `computeEarnings`는
`isDayOff(s.dayOverrides, shift.startMs)`로 부른다. `Settings`가 아니라
override 목록만 받는 건 `calendar.ts`가 설정 타입을 모르게 두려는 것이다. `now`로 판정하면 야간근무가 자정을
넘는 순간 다음 날이 공휴일인지에 따라 근무 중에 금액이 0이 된다. 시작일로
보면 주간근무에서는 결과가 같고(시프트가 오늘 시작하므로) 야간근무만
바로잡힌다.

### 3.3 타입 변화

```ts
export type Phase = 'before' | 'working' | 'lunch' | 'after' | 'dayoff'

export interface Earnings {
  // ...
  /** 휴무일이면 null. 시계 링에 그릴 근무 구간이 없다는 뜻 */
  shift: Shift | null
}
```

휴무일이면 `earned: 0`, `progress: 0`, `perSecond: 0`, `shift: null`.

시프트를 만들어두고 UI가 알아서 무시하길 기대하는 것보다, 없다는 걸
타입으로 말하는 편이 안전하다.

### 3.4 웹 UI 반영

**휴무일에는 `hideAmount` 설정과 무관하게 가리기 화면을 보여준다.**
가리기 상태는 이미 *날짜(크게) + 현재 시각 + 빈 상태줄* 이고, `shift`가
`null`이라 진행 링도 그려지지 않는다. 쉬는 날에 앱이 그대로 시계앱이 된다.

휴무일 전용 문구를 새로 만들지 않는다. 가릴 금액이 없으므로 그날은
가리기 토글 버튼을 숨긴다.

자정부터 출근 전까지는 `phase: 'before'`이므로 기존 화면이 그대로
`출근까지 HH:MM:SS`를 보여준다. 금액만 어제 총액에서 ₩0으로 바뀐다.

## 4. 맥 앱 구조

```
macos/
  SalaryClockCore/        Swift Package — 도메인 순수 함수 + 테스트
  SalaryClockApp/         Swift Package — 메뉴바, 팝오버, 설정 창
scripts/
  bundle-app.sh           swift build → SalaryClock.app
  install-app.sh          /Applications 설치
  generate-palette-swift.ts   palette.json → Palette.swift
```

Xcode 프로젝트를 두지 않는다. `.pbxproj`는 손으로 쓰기 어렵고 diff가
읽히지 않아 리뷰가 불가능한 반면, `Package.swift`와 20줄짜리 번들
스크립트는 둘 다 읽힌다. `swift build`가 AppKit·SwiftUI를 그대로
컴파일하고, `.app` 번들은 디렉터리 구조 + `Info.plist` + ad-hoc
서명이면 끝이다.

`SalaryClockApp` 패키지 안은 다시 세 타깃으로 나뉜다:

```
SalaryClockApp/
  Sources/SalaryClockAppLib/   메뉴바 · 팝오버 · 설정 창 전부 (라이브러리 타깃)
  Sources/SalaryClockApp/      main.swift 하나만 (실행 타깃)
  Tests/SalaryClockAppTests/   SalaryClockAppLib을 테스트
```

계획대로면 테스트 타깃이 실행 타깃(`executableTarget`)을 바로 의존하는데,
`main.swift`의 top-level 코드가 테스트 번들에 함께 링크되면 `main` 심볼이
충돌할 수 있다. 그래서 `main.swift`만 남긴 실행 타깃과, 나머지 전부를
담은 라이브러리 타깃으로 쪼갰다 — 테스트는 라이브러리 쪽만 의존한다.
번들 스크립트가 찾는 실행 파일 이름(`SalaryClockApp`)은 그대로다.

`SalaryClockAppLib`은 `SalaryClockCore`를 의존한다. `LSUIElement = true`로
Dock 아이콘 없이 메뉴바에만 상주한다.

### 4.1 메뉴바

`NSStatusItem`(`variableLength`)의 버튼에 아이콘과 타이틀을 함께 건다.

**타이틀 폰트는 `NSFont.monospacedDigitSystemFont`를 쓴다.** 이러면
`83,412` → `83,418`처럼 자릿수 모양이 바뀌어도 글자 폭이 고정돼 왼쪽
메뉴바 항목들이 밀리지 않는다. 메뉴바는 macOS 시스템 영역이므로 여기만은
웹 글꼴이 아니라 시스템 글꼴을 쓴다 — 다른 메뉴바 항목과 나란히 서야 한다.

| 상태 | 메뉴바 |
|---|---|
| `working` / `lunch` | `◔ ₩83,412` |
| `after` | `● ₩166,667` |
| `before` | `○ ₩0` |
| `dayoff` | `○` (아이콘만) |
| `hideAmount`가 켜짐 | `○` (아이콘만) |

`hideAmount`가 켜져 있으면 금액 자리에 현재 시각을 넣지 않는다. macOS
기본 시계와 나란히 중복되고, 회의 중에 가장 가리고 싶은 게 메뉴바 금액이다.

아이콘은 하루 진행률만큼 차오르는 링이다. 웹 시계의 바깥 진행 링과 같은
색(`emerald-500`)을 쓴다. 1분에 한 번만 다시 그리면 된다.

### 4.2 타이머

`Timer` 간격을 `RunLoop.common` 모드에 등록한다. 기본 모드로만 등록하면
메뉴나 팝오버를 여는 순간 숫자가 멈춘다.

**간격은 고정 1초가 아니라 사용자 설정이다(0.1~10초, 기본 1초).**
초기 설계에서 1초로 고정했던 근거("0.1초면 메뉴바가 꿈틀거린다")는
4.1의 `attributedTitle` 폭 고정으로 사라졌다. 남는 비용은 배터리뿐이라
(10Hz로 깨우면 깊은 절전에 못 들어간다), 설정 창에서 숫자로 직접 바꾸게
했다(4.4). 이 값은 웹과 공유하는 `Settings`가 아니라 맥 전용 저장소에
있다(4.5).

**매 tick마다 `Date()`로 전부 다시 계산한다.** 웹앱의 설계 원칙 ①을
그대로 가져오는 것이다. 누적하지 않으므로 타이머가 드리프트하든 절전에서
깨어나든 다음 tick에 저절로 맞는다.

팝오버가 열려 있는 동안만 0.1초 간격으로 올려 소수점 1자리가 흐르게
하고, 닫히면 설정된 간격으로 되돌린다 — 이 동작은 갱신 주기 설정과
무관하게 유지된다. 웹이 소수 1자리를 쓰는 이유가 그대로 적용된다 —
정수만 쓰면 초당 5.8원일 때 또각또각 끊겨 보인다.

### 4.3 팝오버

`NSPopover` + SwiftUI. 웹 메인 화면에서 시계·금액·상태줄만 떼어낸
축소판이고, **배치와 글꼴과 색은 웹과 같다** (5장).

```
╭────────────────╮
│          ◐ 🙈 ⚙ ⏻│   아이콘 4개 — 테마·가리기·설정·종료, 우상단
│    ╱ 12  ╲      │   MinimalFace — 웹 SVG를 수치 그대로 옮김
│   9   ┼   3    │
│    ╲  6  ╱      │
│                 │
│  ₩83,412.4      │   EarningsDisplay — 정수부 + 소수부 색 분리
│  +5.8 / 초      │
│  퇴근까지 04:00:00│   StatusLine
╰────────────────╯
```

`오늘 벌어들인 금액` 라벨과 `세전`/`실수령` 배지는 웹과 같이 금액 위에
둔다. 팝오버가 좁으므로 웹의 `text-5xl`을 그대로 쓸 수는 없고, 5.3의
비례 축소 규칙을 따른다.

네 아이콘은 텍스트 버튼이 아니라 SF Symbols 아이콘이다(사용자 요청) —
웹도 아이콘이라 오히려 충실도가 올라간다. 순서는 테마 · 가리기 · 설정 ·
종료이고 우상단에 모인다(웹 `page.tsx`의 `right-4 top-4` 클러스터와 같은
배치). 220pt 팝오버에 네 개가 여유 있게 들어간다.

**테마 토글**은 밝게와 어둡게 둘만 오간다. 저장된 값이 없으면
(`hasStored == false`) `@Environment(\.colorScheme)`로 기기 설정을 따르고,
한 번이라도 저장하면 그 값에 고정된다 — 웹 `loadSettings`와 같은 규칙이다.
"기기 설정 / 밝게 / 어둡게" 세 상태를 순환한다는 말은 양쪽 플랫폼 모두에서
사실이 아니다: 한 번 저장되고 나면 기기 설정을 다시 따르게 만드는 경로가
없다(설정을 통째로 지우는 것 말고는). 설정 창(4.4)도 같은 `hasStored` 기준으로
테마를 적용해 팝오버와 어긋나지 않는다.

**가리기 토글**은 상태줄의 일부(`· 남은 ₩X` 접미)가 아니라 상태줄
전체를 비운다. 웹이 원래 그렇게 하는 이유가 그대로 적용된다 —
"퇴근까지"라고 써 붙이면 가린 티가 난다. 문구가 하나라도 남으면 가리기의
목적("옆에서 보면 그냥 시계로 보이는 것")이 깨진다.

### 4.4 설정 창

`NSWindow` + SwiftUI. **남기는 항목의 배치·문구·스타일은 웹
`SettingsPanel`을 그대로 따른다.** 제외한 항목(얼굴 캐러셀)은 자리째
빼고, 남은 것의 순서는 웹과 같게 둔다. 다크모드 토글과 가리기 토글은
이 창이 아니라 팝오버에 있다(4.3) — 웹도 그 둘은 설정 패널이 아니라
메인 화면에 둔다.

macOS 기본 `Form` 스타일(회색 배경, 오른쪽 정렬 라벨)을 쓰지 않는다 —
그러면 웹과 다른 화면이 된다.

| 항목 | 비고 |
|---|---|
| 급여 | 연봉 / 월급 / 시급. 억·만 단위 보조 표시(`formatKoreanUnits`) 포함 |
| 근무 시작·종료 | |
| 점심 | on/off. UI는 시작·종료 두 칸으로 받고, 저장은 시작 시각 + 무급 분으로
한다 — 시작을 바꾸면 무급 길이를 유지한 채 구간이 통째로 이동한다 |
| 실수령액 기준 | 공제율은 자동 추정 또는 직접 입력(0~90%). 비우면 추정치로 되돌아간다 |
| 근무일수 | 자동(평일 − 공휴일) / 달력에서 날짜 찍기 / 직접 입력 세 모드. 모드는
직접 고르지 않는다 — 숫자 칸을 고치면 manual로, 달력에서 날짜를 찍으면
calendar로 행동에서 넘어간다. "자동 N일로" 링크가 auto로 돌아가는 유일한
통로이고, 눌러도 찍어둔 `dayOverrides`는 안 지운다 |
| 로그인 시 자동 실행 | `SMAppService.mainApp.register()` — 웹에 없는 항목 |
| 메뉴바 갱신 주기 | 0.1~10초, 기본 1초. `초` 접미의 숫자 입력칸 + 안내
문구 한 줄. 로그인 자동 실행 옆에 둔다(둘 다 맥 전용 옵션) — 웹에
없는 항목이고 팝오버가 아니라 여기 있다(4.2) |

공휴일 표가 없는 해(2028~)에는 주말만 근무일수 계산에 반영하고,
웹과 같은 문구로 그 사실을 알린다. 달력을 펼쳤는지·어느 달을
보여주는지는 `Settings`에 저장하지 않는 순수 뷰 상태다 — 웹도 같다.

### 4.5 저장

`UserDefaults`에 `Codable` 구조체로 저장한다. 웹의 zod 스키마에
대응하는 검증은 값 검증 함수로 옮긴다 — 저장된 값이 규칙을 어기면
기본값으로 되돌린다.

**맥 전용 설정(메뉴바 갱신 주기)은 공유 `Settings`에 넣지 않는다.**
`Settings`는 웹과 공유하는 도메인 모델이고 `shared/golden/settings.json`이
그 필드를 고정한다 — 여기 필드를 더하면 골든이 깨지고 웹 스키마까지
건드려야 하는데, 갱신 주기는 웹에 대응물이 없는 맥만의 표시 취향이라
도메인이 아니다. 별도의 `UserDefaults` 키를 쓰는 작은 저장소
(`AppPreferences`)를 두고, `SettingsStore`와 같은 규칙(검증 실패 시
기본값, 값이 바뀌면 알림)을 따른다.

**웹앱과 설정이 이어지지 않는다.** 웹은 브라우저 `localStorage`에
저장하고 맥 앱은 `UserDefaults`에 저장한다. 맥에서 설정을 한 번 새로
넣어야 한다. (Tauri를 골랐더라도 웹뷰의 `localStorage`는 사파리·크롬과
별개라 마찬가지였다.)

## 5. 디자인 이식

"웹과 같아 보인다"를 눈대중에 맡기지 않는다. 색과 글꼴은 값으로 옮기고,
도형은 수치로 옮긴다.

### 5.1 팔레트

웹은 Tailwind v4 기본 팔레트에서 `slate`·`emerald`를 쓰고, 달력(4.4)이
`rose`·`sky` 몇 토큰을 더했다(주말·공휴일·직접 지정 표시). 실제로
화면에 칠해지는 배경·본문 색은 `app/page.tsx`의 `<main>`이 지정하는
**`surface`** 토큰이다. `globals.css`의 `--background`/`--foreground`는
`<main>`이 항상 덮어쓰는 **폴백**(`bodyFallback`)이라 화면에는 보이지
않는다 — `palette.json`이 이 둘을 별도 키로 나눠 담는다.

| 용도 | 밝게 | 어둡게 |
|---|---|---|
| 배경 (`surface`) | `white` → `#ffffff` | `slate-950` → `#020618` |
| 본문 (`surface`) | `slate-900` | `slate-100` |
| 배경 폴백 (`bodyFallback`, 화면에 안 쓰임) | `#fff` | `#0a0a0a` |
| 본문 폴백 (`bodyFallback`, 화면에 안 쓰임) | `#171717` | `#ededed` |
| 시계 바늘 (시·분) | `slate-800` | `slate-100` |
| 문자판 눈금 | `slate-400` | `slate-500` |
| 링 — 근무 구간 | `slate-200` | `slate-700` |
| 링 — 점심 지우개 | 배경색 (`surface`) | 배경색 (`surface`) |
| 링 — 점심 파선 | `slate-300` | `slate-600` |
| 진행 링 · 초침 · 중심점 | `emerald-500` | `emerald-500` |
| 초당 적립액 | `emerald-600` | `emerald-400` |
| 보조 텍스트 | `slate-500` | `slate-400` |
| 금액 소수부 · 흐린 텍스트 | `slate-400` | `slate-500` |
| 배지 테두리 | `slate-200` | `slate-700` |
| 달력 표시 (주말/공휴일/직접 지정) | `rose`·`sky`·`emerald`·`slate` 토큰 | 같음 |

점심 구간은 링을 굵게 덧그어 지우는 방식이라 **배경과 같은 색이어야
한다.** 이전 판(v3 팔레트 기준)에서는 다크모드 배경 폴백이 `#0a0a0a`,
지우개에 쓰는 `slate-950`이 `#020617`이라 정확히 같지 않다고 적었는데,
그 우려는 착오였다 — 화면에 실제로 칠해지는 다크모드 배경은 폴백이
아니라 `surface`(`slate-950`)이고, v4의 `slate-950`은 `#020618`이다.
지우개 색과 배경 색이 **정확히 일치한다.**

배경·본문 색(`surface`·`bodyFallback`)은 `app/globals.css`와
`app/page.tsx`에서 그대로 가져온 값이다. `slate`·`emerald`·`rose`·`sky`
값은 Tailwind v4가 oklch로 정의하므로, **빌드된 CSS에서 실제 사용된
색만 뽑아** `shared/golden/palette.json`으로 내보내고 `Palette.swift`를
거기서 생성한다. 손으로 hex를 적지 않는다.

`Palette.swift` 생성기는 `hex`가 3자리(`#fff`, `white` 토큰이 그 경우다)일
수 있고 `lab`이 `null`일 수 있음을 처리해야 한다. 이번 버전은 sRGB
`hex`만 쓰고 `lab`은 JSON에 남겨둔다 — 광색역 `lab()` → Display P3
변환을 눈으로 검증할 수단이 없는 채로 넣을 작업은 아니다.

다크모드는 웹과 같은 규칙을 그대로 옮긴다. 저장된 테마가 없으면
(`hasStored == false`) SwiftUI의 `@Environment(\.colorScheme)`로 기기 설정을
따르고, 한 번이라도 저장했으면 그 값에 고정한다. 저장된 값이 없을 때는 기기 외형을
`Settings.theme`의 시작값으로 심어 둬, 첫 저장에 그 값이 그대로 딸려
나간다(웹 `loadSettings`가 하는 일과 같다). 팝오버에 있는 토글 자체는
밝게/어둡게 둘만 오간다 — 기기 설정으로 되돌아가는 상태는 토글로 갈 수
없다(4.3).

### 5.2 글꼴

| 대상 | 웹 | 맥 |
|---|---|---|
| 금액·시각·상태줄 (`font-mono`) | Geist Mono | 시스템 `.monospaced` (SF Mono) |
| 그 외 본문 | Arial | **SF Pro (시스템 글꼴)** — 스펙과 어긋난 채로 구현됨, 아래 참고 |
| 메뉴바 타이틀 | — | 시스템 글꼴 (4.1) |

**Geist Mono를 앱에 번들하지 않기로 했다.** OFL 라이선스라 번들 자체는
가능하지만, 라이선스 파일과 `ATSApplicationFontsPath` 설정이 더 필요한
데 비해 그 차이가 드러나는 곳은 팝오버 안의 22pt 숫자 몇 개뿐이다.
SwiftUI `.monospaced` 시스템 글꼴로 대신하고, 웹과 나란히 띄워 봐도
거슬리지 않는다는 걸 확인했다(4.3 이식 검증). 거슬리면 그때 번들을
붙인다 — 지금은 하지 않는다.

본문이 Arial인 것은 `globals.css`의 `body { font-family: Arial, ... }`
때문이다. `--font-geist-sans`를 html에 걸어놓고도 body 선언이 이기고
있어서, **웹에서 실제로 보이는 건 Arial이다.**

**여기는 충실도 갭이다. 숨기지 않고 적어 둔다.** 이 절은 원래 "디자인을
맞추라는 요구에 따라 맥도 Arial을 쓴다"고 요구했지만, `macos/` 어디에도
글꼴을 지정하는 코드가 없다 — 모든 라벨이 `.font(.system(...))`, 즉 SF Pro다.
요구가 구현되지 않았고 아무도 잡아내지 못한 채 실행이 끝났다. 요구를
조용히 고쳐 쓰는 대신, 요구와 구현이 달랐다는 사실을 그대로 남긴다.

그 위에서 내린 결정은 **SF Pro를 그대로 둔다**이다. 이유는 둘이다.
(1) 웹의 Arial은 의도된 브랜드 선택이 아니라 Geist Sans를 덮어쓴
`globals.css`의 잔재다 — 맞춰야 할 디자인이라기보다 웹 쪽에서 걷어낼
후보에 가깝다. (2) 메뉴바 팝오버는 시스템 크롬 옆에 붙어 있어서, 여기서만
다른 sans를 쓰면 macOS에서는 "웹과 같은 화면"이 아니라 "남의 앱"처럼 보인다.
숫자(`font-mono`) 쪽은 이미 시스템 `.monospaced`를 쓰기로 한 것과 같은 판단이다.

이 결정을 뒤집으려면 맥에서 본문 글꼴을 Arial로 지정하는 것(한 줄짜리
작업이다)이 아니라, 웹의 `body` 선언을 어떻게 할지부터 정해야 한다.

`tabular-nums`는 `NSFont`의 `monospacedDigit` 설정으로 대응한다.

### 5.3 치수

시계는 `components/clock/MinimalFace.tsx`의 `viewBox="0 0 200 200"`
좌표계를 그대로 SwiftUI `Canvas`로 옮긴다.

| 값 | |
|---|---|
| 중심 | `CX`, `CY` (`clock/types.ts`) |
| 진행 링 반지름 | 92 |
| 문자판 반지름 | 76 |
| 링 두께 | 5 |
| 점심 구간 — 지우개 | 9 |
| 점심 구간 — 파선 | 1.5, `dash [2, 3]` |
| 눈금 길이 | 3의 배수는 11, 나머지는 5 |
| 눈금 두께 | 3의 배수는 3, 나머지는 1.5 |
| 시침 | `+10` ~ `-42`, 두께 5 |
| 분침 | `+12` ~ `-62`, 두께 3 |
| 초침 | `+16` ~ `-68`, 두께 1.5 |
| 중심점 | 반지름 3.5 |

선 끝은 전부 `round`다. **바늘 회전에 애니메이션을 걸지 않는다** —
웹과 같은 이유로, 360°에서 0°로 넘어갈 때 역방향으로 한 바퀴 돈다.
매 tick마다 각도를 직접 찍으므로 필요도 없다.

웹은 `html { font-size: clamp(...) }`로 UI 전체를 비례 축소한다. 맥은
팝오버 크기가 고정이므로, 같은 효과를 **기준 글꼴 크기 하나를 정하고
나머지를 그에 대한 배수로 쓰는 것**으로 얻는다. 웹의 Tailwind 단계
(`text-xs` 0.75 / `text-sm` 0.875 / `text-5xl` 3)를 그 배수로 삼는다.

### 5.4 문구

화면에 나오는 한국어는 웹과 글자까지 같게 쓴다: `오늘 벌어들인 금액`,
`세전` / `실수령`, `퇴근까지 HH:MM:SS`, `점심시간 HH:MM:SS`,
`출근까지 HH:MM:SS`, `· 남은 ₩0`.

점심 문구는 원래 `점심시간 · 재개까지 HH:MM:SS`였다가 `점심시간 HH:MM:SS`로
줄였다 — 메뉴바 상태줄이 폭에 걸려 잘리는 문제(`00:33:…`)를 겪었고,
글자를 줄이는 대신 문구 자체를 줄이는 쪽을 택했다. 웹 `StatusLine.tsx`도
같은 문구로 맞췄다.

**퇴근 후 문구는 고정 문장이 아니라 다음 근무일까지의 간격에 따라 넷
중 하나를 고른다** (`lib/afterWork.ts`):

| 상황 | 문구 |
|---|---|
| 다음 근무일이 내일 | `오늘도 고생하셨어요` |
| 내일은 쉬고, 이번 주 안에 또 출근 | `오늘도 고생하셨어요, 푹 쉬세요` |
| 다음 근무일이 다음 주 | `이번 주도 고생하셨어요` |
| 연휴 (4일 이상 쉼) | `연휴 잘 보내세요` |

"다음 주"라고 쓰지 않은 이유: 수요일 퇴근 + 목요일 공휴일 + 금요일
출근처럼, 다음 근무일이 이번 주 안인데도 "다음 주"라고 잘못 말하게 되는
경우가 있다. 다음 근무일까지의 간격과 주 경계로 가른다.

금액·시각 포맷도 `lib/format.ts`와 같은 규칙을 따른다. 특히 **금액은
항상 내림한다** — 반올림하면 아직 벌지 않은 1원이 먼저 뜬다.

| `lib/workdays.ts` | 85 | `calendar` 모드 분기까지 전부 (4.4로 들어왔다) |
| `lib/calendar.ts` | 108 | `isDefaultOff`·`isDayOff`에 더해 `monthCells`·`dateKey`·`toggleOverride`·`clearMonthOverrides` (`MonthCells.swift`) |
| `lib/afterWork.ts` | 37 | 퇴근 후 문구의 kind만 — 실제 한국어 문장은 UI가 갖는다 (5.4) |
| `lib/clock.ts` | 116 | `minimal`에 필요한 각도·호 계산만 |
| `lib/format.ts` | 75 | `NumberFormatter` 기반으로 다시 씀 |

옮기지 않는 것: `settings-store.ts` (웹 전용).

**웹과 같은 규칙을 지킨다: 순수 함수이고, 현재 시각을 인자로 받으며,
`Date()`를 직접 부르지 않는다.** 이 규칙이 테스트 가능성의 전부다.

## 7. 의존 방향

```
time → settings → shift → { salary, clock }
                    ↑
                 calendar → holidays
                    ↑
                 workdays
```

웹과 같다. 순환이 없다.

## 9. 테스트 전략

역할을 섞지 않는다. **정확성은 각자의 유닛 테스트가 보고, 일치성은
골든 파일이 본다.**

### 9.1 골든 파일

```
shared/golden/
  earnings.json      computeEarnings 입력 → 기대 출력
  shift.json         resolveShift
  deductions.json    estimateDeductions
  workdays.json      effectiveWorkDays / isDayOff
  settings.json      위 파일들이 이름으로 가리키는 설정 묶음
  palette.json       웹에서 실제로 쓰는 색 토큰 (5.1)
  format.json        formatWon / formatKoreanUnits / formatDuration 등 (lib/format.ts)
  clock.json         바늘 각도 · 문자판 호 (lib/clock.ts)
  calendar.json      월별 날짜 상태 — work/weekend/holiday/custom-off/custom-work (lib/calendar.ts monthCells)
  afterWork.json     퇴근 후 문구의 kind — tomorrow/restThisWeek/nextWeek/longBreak (lib/afterWork.ts, 5.4)
```

vitest와 Swift Testing이 같은 파일을 읽는다. 규칙이 갈라지는 순간 한쪽
테스트가 실패한다. `palette.json`은 테스트가 아니라 `Palette.swift`
생성에 쓰인다.

**시각은 `[2026, 8, 22, 9, 0, 0]` 배열로 적고 양쪽이 각자 로컬 타임존으로
해석한다.** (월은 0-based) epoch ms를 박으면 "기대값을 하드코딩한 UTC
오프셋으로 만들지 말 것"이라는 기존 제약이 깨진다.

부동소수는 상대 오차 `1e-9`로 비교한다.

### 9.2 골든 생성

손으로 쓰지 않고 **웹 구현에서 뽑아 커밋한다.** 규칙의 단일 출처가
`lib/`이므로, 골든은 "Swift가 `lib/`와 같은 답을 내는가"만 본다.

웹 규칙이 바뀌면 재생성하고, 그때 나오는 diff가 곧 Swift에서 고쳐야 할
목록이 된다.

골든이 웹의 버그를 굳힐 위험은 있다. 그건 웹의 유닛 테스트가 막을 일이지
골든이 할 일이 아니다.

### 9.3 케이스

경계만 촘촘히 깐다.

- 출근 직전 / 직후
- 점심 시작 / 끝
- 퇴근 직후
- 자정 직전 / 직후
- 휴무일 (주말, 공휴일, `dayOverrides`로 지정한 날)
- 월말
- 공휴일 표가 없는 해 (2028)
- 급여 3종 (연봉 / 월급 / 시급)
- 실수령 on / off

### 9.4 기존 웹 테스트

**기존 `resolveShift` 테스트 12개는 새 규칙에서도 전부 그대로 통과한다.**
대입해 확인했다. 버그가 나는 구간이 좁아서다 — 09:00–18:00 설정에서
"가장 가까운"이 어제 시프트를 고르는 건 자정부터 01:30까지뿐이고(어제
18:00과 오늘 09:00의 중간), 기존 테스트의 한밤중 케이스는 02:00이라
그 구간 밖이다.

고칠 테스트는 없고 추가만 한다: 3.1 표의 00:30 케이스, 휴무일 케이스,
그리고 야간근무가 자정을 넘을 때 시작일 기준으로 판정되는지(3.2).

### 9.5 디자인은 테스트하지 않는다

팔레트는 생성으로 맞추고, 치수는 5.3의 표를 보고 옮긴다. 화면이 같은지는
웹과 나란히 띄워 눈으로 본다. 스냅샷 테스트를 두지 않는다 — 두 플랫폼의
렌더링이 픽셀 단위로 같을 수 없어서 거짓 실패만 늘어난다.

## 10. 빌드와 배포

`scripts/install-app.sh`로 로컬 빌드해 `/Applications`에 넣는다.
**본인 기계에서 빌드한 ad-hoc 서명 앱이라 Gatekeeper가 막지 않는다.**
이슈 #1이 걱정하던 "우클릭으로 열기"나 `xattr -dr com.apple.quarantine`가
필요 없다.

```bash
./scripts/install-app.sh
open /Applications/SalaryClock.app
```

`install-app.sh`는 `scripts/bundle-app.sh release`로 번들을 만들고(4장),
돌고 있는 이전 버전을 먼저 내린 뒤(실행 중인 번들을 덮어쓰면 다음 실행이
깨진다) `/Applications`에 복사한다.

**이 저장소는 `~/Documents` 아래에 있어 iCloud Drive가 동기화한다.**
iCloud가 빌드 산출물에 붙이는 확장 속성 때문에 기본 `.build` 경로로는
`codesign`이 "resource fork, Finder information, or similar detritus not
allowed"로 실패한다 — `swift build`·`swift test`를 이 저장소에서 직접
돌리려면 항상 iCloud 동기화 밖의 캐시 경로를 `--scratch-path`로 줘야
한다. `bundle-app.sh`·`install-app.sh`는 내부에서 이미 처리하지만, 손으로
돌리는 명령은 각자 지정해야 한다:

```bash
swift test --package-path macos/SalaryClockCore --scratch-path "$HOME/Library/Caches/salaryclock/core"
swift test --package-path macos/SalaryClockApp  --scratch-path "$HOME/Library/Caches/salaryclock/app"
```

`npm run swift:test:core` / `npm run swift:test:app`가 같은 경로로 이미
감싸져 있다.

같은 이유로 **조립된 `.app` 자체도 문제가 될 수 있다.** `bundle-app.sh`가
결과물을 두는 `macos/build/`는 스크래치 경로가 아니라 저장소 안이라
iCloud 동기화 대상이다. 빌드 직후 `.app`에 iCloud가 `com.apple.FinderInfo`·
`com.apple.fileprovider.fpfs#P` 같은 확장 속성을 붙이면 마지막 `codesign`
단계가 같은 이유로 실패한다. `bundle-app.sh`는 서명 직전에 `xattr -cr "$APP"`로
이 속성을 지워서 대응한다.

Apple Developer 계정도 GitHub Actions도 필요 없다. 남에게 배포하고
싶어지면 그때 붙인다.

## 11. 저장소 배치

```
SalaryClock/
  app/ components/ hooks/ lib/    웹. 구조 그대로
  shared/golden/                  양쪽이 읽는 기대값과 팔레트
  macos/                          맥 앱
```

한 저장소에 둔다. 이 설계의 유일한 진짜 리스크가 "도메인 규칙이 두 벌"인데,
저장소를 나누면 그 리스크를 키우는 쪽으로 움직인다. 3장의 규칙 변경이
정확히 그 사례다 — TypeScript와 Swift를 같이 고쳐야 하고, 한 커밋에 담기면
한쪽만 고치고 잊기가 구조적으로 어려워진다. 디자인도 마찬가지다.

골든 파일을 공유하려면 저장소가 나뉜 경우 서브모듈이나 패키지 배포가
필요한데, 혼자 쓰는 프로젝트에 그건 과하다.

Next.js 빌드는 `app/` 기준이라 `macos/`가 생겨도 Vercel 배포에 영향이 없다.

**나누는 게 맞아지는 시점:** 맥 앱이 자기 릴리스 주기를 갖거나, 웹을 접고
데스크톱만 가져갈 때. 그때는 `lib/`가 단일 출처일 이유가 사라진다.

## 12. 작업 순서

1. `lib/` 규칙 변경 (3장) + 웹 UI 반영 — 기존 테스트 수정 포함
2. 골든 파일 + 팔레트 추출 스크립트 (9장, 5.1)
3. `SalaryClockCore` 포팅 + 골든으로 검증 (6장)
4. 메뉴바 앱 — `NSStatusItem` + 타이머 (4.1, 4.2)
5. 팝오버 + 시계 얼굴 이식 (4.3, 5.3)
6. 설정 창 (4.4)
7. `/Applications` 설치, 로그인 시 자동 실행 (4.4, 10장)

1번은 그 자체로 웹앱 버그 수정이라 **여기서 멈춰도 이득이 남는다.**
3번까지 끝나면 어려운 부분은 다 끝난 셈이고, 4~7은 평범한 AppKit·SwiftUI
작업이다.

## 13. 확장 여지

원래 여기 있던 "달력 근무일 지정"과 "다크모드 고정 토글"은 실행 중
사용자 요청으로 이미 들어갔다 (2장 "뒤집힌 제외 항목", 4.3, 4.4). 남은
확장 여지는 아래뿐이다.

- 시계 얼굴 10종 — 5.3과 같은 방식으로 하나씩 늘린다. 팝오버를 키울 때 의미가 생긴다
- Windows — 트레이에 글자를 못 넣으므로 항상-위 작은 창으로 다시 설계해야 한다.
  이슈 #1의 `/widget` 라우트 구상이 그쪽 출발점이다
- 배포 — 코드 서명 + 공증 + GitHub Releases. 이슈 #1의 `tauri-action` 자리에
  `xcodebuild` + `notarytool`이 들어간다

### 열린 질문 — 일요일 밤에 시작한 야간근무는 근무 시프트인가

`resolveShift`가 "끝난 시프트와 오늘 출근 중 가까운 쪽"을 고르게 바뀐 뒤로
(3.2) 이 질문이 닿는 범위가 줄었다. 야간근무(22:00–06:00)에서 두 시각의
중간점은 14:00이다. 그 전까지는 방금 끝난 어젯밤 시프트가, 그 뒤로는 오늘
출근할 시프트가 걸린다.

그래서 월요일 한낮(14:00 이후)은 이제 월요일 22:00 시프트를 골라 `before`가
나온다. 남은 구간은 자정~14:00이다. 이때는 일요일 22:00에 시작한 시프트가
걸리고, `isDayOff`가 시작일(일요일)로 판정하므로 화면이 `dayoff`로 접힌다.
월요일 새벽 내내 실제로 일하고 06:00에 퇴근한 사람이 그 돈을 못 보는 것이
지금 남아 있는 증상이다. (같은 규칙이 공휴일에도 그대로 나온다: 2026-09-24
추석에 14:00 정각까지는 수요일 밤에 번 돈을 `after`로 보여주고, 그 뒤로는
목요일 시프트를 골라 `dayoff`가 된다. 중간점 정각은 동점이라 끝난 쪽을
남긴다 — 방금 번 돈을 먼저 지우지 않는다.)

제대로 고치려면 여전히 "일요일 밤에 시작해 월요일 아침에 끝나는 시프트를
근무로 볼 것인가"를 먼저 정해야 한다. 근무로 본다면 휴무일 판정을 시작일이
아니라 종료일이나 시프트 전체로 옮겨야 하고, 그러면 3.2가 막은 자정 넘김
문제가 반대 방향으로 돌아온다. 설계 결정이 나기 전까지는 `isDayOff`의 기준을
건드리지 않는다 — 규칙은 `resolveShift` 하나로 유지하고 별도 장치를 두지 않는다.
