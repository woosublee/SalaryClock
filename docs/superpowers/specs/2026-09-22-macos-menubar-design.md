# SalaryClock macOS 메뉴바 앱 설계 문서

작성일: 2026-09-22

## 1. 개요

SalaryClock을 macOS 메뉴바 앱으로 옮긴다. 종일 띄워놓고 금액이 쌓이는 걸
곁눈으로 보는 게 목적이므로, **금액을 메뉴바에 직접 텍스트로 띄우고**
클릭하면 시계와 상세가 담긴 팝오버가 떨어진다.

```
메뉴바  …  ◔ ₩83,412  ▸  🔋 100%  화 오후 1:24
                  │
         클릭 ───▸ ╭────────────────╮
                  │    ╱ 12  ╲      │
                  │   9   ┼   3    │
                  │    ╲  6  ╱      │
                  │                 │
                  │  ₩83,412.4      │
                  │  +5.8 / 초      │
                  │  퇴근까지 04:00:00│
                  │  [설정]  [종료]  │
                  ╰────────────────╯
```

네이티브 Swift로 만든다. 웹앱은 그대로 두고, 두 앱이 `shared/golden/`의
기대값 파일을 공유해 계산 규칙과 디자인 토큰이 갈라지지 않게 한다.

## 2. 범위

### 포함

- 메뉴바 타이틀에 적립 금액 표시 (1초마다 정수 갱신)
- 클릭 시 팝오버: 시계 1종, 금액, 초당 적립액, 퇴근까지 남은 시간
- 설정 창: 급여, 근무시간, 점심, 실수령액 기준, 로그인 시 자동 실행
- 웹과 공유하는 도메인 규칙 변경 (휴무일, 자정 초기화)
- 두 구현의 일치를 검증하는 골든 파일

### 제외 (YAGNI)

- Windows 지원 — 윈도우 트레이는 아이콘만 달 수 있고 글자를 못 넣는다.
  이 앱의 주 화면이 성립하지 않으므로 다른 설계가 필요하고, 그건 별도 과제다
- 시계 얼굴 10종 — 팝오버가 작아 차이가 드러나지 않는다. `minimal` 1종만 옮긴다
- 달력으로 근무일 지정 (`workDaysMode: 'calendar' | 'manual'`) — 맥 앱은 `auto` 고정
- 다크모드 **토글** — 웹의 세 상태(기기 설정 / 밝게 고정 / 어둡게 고정) 중
  기기 설정을 따르는 기본 동작만 가져간다
- 코드 서명, 공증, 배포 — 본인 기계에서 빌드해 쓴다 (10장)

**제외한 건 기능이지 디자인이 아니다.** 옮기는 화면은 웹과 같아 보여야
한다. 색·글꼴·도형 수치를 눈대중으로 맞추지 않고 값으로 옮긴다 (5장).

### 결정을 되돌린 것

이슈 #1은 Tauri v2 + GitHub Actions 빌드로 결정돼 있었다. 그 결정은
**(1) 개발 기계가 Windows 11이고 (2) Windows도 타깃**이라는 두 전제에서
나왔는데, 작업 기계가 Xcode가 깔린 맥으로 바뀌었고 Windows는 범위에서
빠졌다. 전제가 모두 사라졌으므로 네이티브로 되돌린다.

Tauri를 유지하면 메뉴바 숫자를 1초마다 갱신하기 위해 웹뷰를 상주시켜야
하는데, macOS가 가려진 `WKWebView`의 타이머를 스로틀할 수 있어 이 앱의
핵심인 "숫자가 흐르는 것"이 보장되지 않는다. 우회하려면 Rust가 타이머를
쥐고 웹뷰는 계획만 넘기는 구조가 되는데, 그러면 숫자를 찍으려고 웹뷰를
상주시키는 꼴이 된다.

대가는 **도메인 규칙이 두 벌이 되는 것** 하나이고, 9장의 골든 파일로
관리한다.

## 3. 도메인 규칙 변경 (웹·맥 공통)

`lib/` 아래에서 고치고 웹앱에도 그대로 반영한다. 규칙의 단일 출처는
계속 `lib/`다.

### 3.1 시프트 선택

`resolveShift`를 세 단계로 다시 쓴다.

```
1. now를 포함하는 시프트가 있으면        → 그것        (working / lunch)
2. 없고, 오늘 안에 끝난 시프트가 있으면  → 그것        (after — 총액 유지)
3. 그 외                                  → 오늘 시작할 시프트 (before — 0원)
```

지금은 "시간적으로 가장 가까운 시프트"를 고른다. 그 규칙은 퇴근 직후
적립액이 0으로 리셋되는 걸 막으려고 넣은 것인데, 자정을 넘긴 뒤에도
어제 시프트가 계속 가장 가까워서 **어제 총액이 그대로 남는 버그**가 있다.

"오늘 안에 끝났는가"로 바꾸면 자정을 특별 취급하지 않고도 초기화가
저절로 나온다.

| 상황 | 지금 | 바뀐 뒤 |
|---|---|---|
| 09–18 근무, 20:00 | 오늘 총액 | 오늘 총액 (2단계) |
| 09–18 근무, 00:30 | **어제 총액** (버그) | ₩0 (3단계) |
| 09–18 근무, 08:00 | ₩0 | ₩0 (3단계) |
| 22–06 야근, 00:30 | 적립 중 | 적립 중 (1단계) |
| 22–06 야근, 07:00 | 방금 끝난 총액 | 방금 끝난 총액 (2단계) |

야간근무는 이 앱의 설계 동인이 아니다. 다만 설정 화면이 22:00–06:00
입력을 여전히 허용하므로, 지원하는 설정이 조용히 깨지게 두지 않는다.
"자정에 리셋"이라고 직접 쓰면 더 짧지만 야근 중에 0이 된다. 위 규칙은
몇 줄 더 쓰는 대신 둘 다 맞는다.

### 3.2 휴무일

지금 `salary.ts`는 요일을 전혀 보지 않아 **토요일에도 돈이 쌓인다.**
판정 재료는 `lib/calendar.ts`에 이미 있다.

```ts
/** 그 날이 쉬는 날인가 — 주말·공휴일에 dayOverrides를 반영한 결과 */
export function isDayOff(s: Settings, now: number): boolean
```

`dayOverrides`는 **`workDaysMode`와 무관하게 반영한다.** 달력에서 "이날은
쉰다"고 찍은 건 근무일수를 어떤 방식으로 세는지와 별개로 참인 사실이다.

### 3.3 타입 변화

```ts
export type Phase = 'before' | 'working' | 'lunch' | 'after' | 'dayoff'

export interface Earnings {
  // ...
  /** 휴무일이면 null. 시계 링에 그릴 근무 구간이 없다는 뜻 */
  shift: Shift | null
}
```

휴무일이면 `earned: 0`, `progress: 0`, `perSecond: 0`, `shift: null`.

시프트를 만들어두고 UI가 알아서 무시하길 기대하는 것보다, 없다는 걸
타입으로 말하는 편이 안전하다.

### 3.4 웹 UI 반영

**휴무일에는 `hideAmount` 설정과 무관하게 가리기 화면을 보여준다.**
가리기 상태는 이미 *날짜(크게) + 현재 시각 + 빈 상태줄* 이고, `shift`가
`null`이라 진행 링도 그려지지 않는다. 쉬는 날에 앱이 그대로 시계앱이 된다.

휴무일 전용 문구를 새로 만들지 않는다. 가릴 금액이 없으므로 그날은
가리기 토글 버튼을 숨긴다.

자정부터 출근 전까지는 `phase: 'before'`이므로 기존 화면이 그대로
`출근까지 HH:MM:SS`를 보여준다. 금액만 어제 총액에서 ₩0으로 바뀐다.

## 4. 맥 앱 구조

```
macos/
  SalaryClock.xcodeproj
  SalaryClock/            앱 타깃 — 메뉴바, 팝오버, 설정 창
  SalaryClockCore/        Swift Package — 도메인 순수 함수 + 테스트
```

앱 타깃은 `SalaryClockCore`를 의존하기만 한다. `LSUIElement = true`로
Dock 아이콘 없이 메뉴바에만 상주한다.

### 4.1 메뉴바

`NSStatusItem`(`variableLength`)의 버튼에 아이콘과 타이틀을 함께 건다.

**타이틀 폰트는 `NSFont.monospacedDigitSystemFont`를 쓴다.** 이러면
`83,412` → `83,418`처럼 자릿수 모양이 바뀌어도 글자 폭이 고정돼 왼쪽
메뉴바 항목들이 밀리지 않는다. 메뉴바는 macOS 시스템 영역이므로 여기만은
웹 글꼴이 아니라 시스템 글꼴을 쓴다 — 다른 메뉴바 항목과 나란히 서야 한다.

| 상태 | 메뉴바 |
|---|---|
| `working` / `lunch` | `◔ ₩83,412` |
| `after` | `● ₩166,667` |
| `before` | `○ ₩0` |
| `dayoff` | `○` (아이콘만) |
| `hideAmount`가 켜짐 | `○` (아이콘만) |

`hideAmount`가 켜져 있으면 금액 자리에 현재 시각을 넣지 않는다. macOS
기본 시계와 나란히 중복되고, 회의 중에 가장 가리고 싶은 게 메뉴바 금액이다.

아이콘은 하루 진행률만큼 차오르는 링이다. 웹 시계의 바깥 진행 링과 같은
색(`emerald-500`)을 쓴다. 1분에 한 번만 다시 그리면 된다.

### 4.2 타이머

`Timer` 1초 간격을 `RunLoop.common` 모드에 등록한다. 기본 모드로만
등록하면 메뉴나 팝오버를 여는 순간 숫자가 멈춘다.

**매 tick마다 `Date()`로 전부 다시 계산한다.** 웹앱의 설계 원칙 ①을
그대로 가져오는 것이다. 누적하지 않으므로 타이머가 드리프트하든 절전에서
깨어나든 다음 tick에 저절로 맞는다.

팝오버가 열려 있는 동안만 0.1초 간격으로 올려 소수점 1자리가 흐르게
하고, 닫히면 1초로 되돌린다. 웹이 소수 1자리를 쓰는 이유가 그대로
적용된다 — 정수만 쓰면 초당 5.8원일 때 또각또각 끊겨 보인다.

### 4.3 팝오버

`NSPopover` + SwiftUI. 웹 메인 화면에서 시계·금액·상태줄만 떼어낸
축소판이고, **배치와 글꼴과 색은 웹과 같다** (5장).

```
╭────────────────╮
│    ╱ 12  ╲      │   MinimalFace — 웹 SVG를 수치 그대로 옮김
│   9   ┼   3    │
│    ╲  6  ╱      │
│                 │
│  ₩83,412.4      │   EarningsDisplay — 정수부 + 소수부 색 분리
│  +5.8 / 초      │
│  퇴근까지 04:00:00│   StatusLine
│  [설정]  [종료]  │
╰────────────────╯
```

`오늘 벌어들인 금액` 라벨과 `세전`/`실수령` 배지는 웹과 같이 금액 위에
둔다. 팝오버가 좁으므로 웹의 `text-5xl`을 그대로 쓸 수는 없고, 5.3의
비례 축소 규칙을 따른다.

### 4.4 설정 창

`NSWindow` + SwiftUI. **남기는 항목의 배치·문구·스타일은 웹
`SettingsPanel`을 그대로 따른다.** 제외한 항목(근무일수 모드와 달력,
얼굴 캐러셀, 다크모드 토글, 가리기)은 자리째 빼고, 남은 것의 순서는
웹과 같게 둔다.

macOS 기본 `Form` 스타일(회색 배경, 오른쪽 정렬 라벨)을 쓰지 않는다 —
그러면 웹과 다른 화면이 된다.

| 항목 | 비고 |
|---|---|
| 급여 | 연봉 / 월급 / 시급. 억·만 단위 보조 표시(`formatKoreanUnits`) 포함 |
| 근무 시작·종료 | |
| 점심 | on/off, 시작 시각, 무급 분 |
| 실수령액 기준 | 공제율은 자동 추정만 |
| 로그인 시 자동 실행 | `SMAppService.mainApp.register()` — 웹에 없는 항목 |

근무일수는 `auto` 고정이고 공휴일 표는 그대로 쓴다. 공휴일 표가 없는
해에는 웹과 같은 문구로 그 사실을 알린다.

### 4.5 저장

`UserDefaults`에 `Codable` 구조체로 저장한다. 웹의 zod 스키마에
대응하는 검증은 값 검증 함수로 옮긴다 — 저장된 값이 규칙을 어기면
기본값으로 되돌린다.

**웹앱과 설정이 이어지지 않는다.** 웹은 브라우저 `localStorage`에
저장하고 맥 앱은 `UserDefaults`에 저장한다. 맥에서 설정을 한 번 새로
넣어야 한다. (Tauri를 골랐더라도 웹뷰의 `localStorage`는 사파리·크롬과
별개라 마찬가지였다.)

## 5. 디자인 이식

"웹과 같아 보인다"를 눈대중에 맡기지 않는다. 색과 글꼴은 값으로 옮기고,
도형은 수치로 옮긴다.

### 5.1 팔레트

웹은 Tailwind v4 기본 팔레트에서 `slate`와 `emerald`만 쓴다. 실제로
쓰이는 토큰은 아래가 전부다.

| 용도 | 밝게 | 어둡게 |
|---|---|---|
| 배경 | `#ffffff` | `#0a0a0a` |
| 본문 | `#171717` | `#ededed` |
| 시계 바늘 (시·분) | `slate-800` | `slate-100` |
| 문자판 눈금 | `slate-400` | `slate-500` |
| 링 — 근무 구간 | `slate-200` | `slate-700` |
| 링 — 점심 지우개 | 배경색 | 배경색 |
| 링 — 점심 파선 | `slate-300` | `slate-600` |
| 진행 링 · 초침 · 중심점 | `emerald-500` | `emerald-500` |
| 초당 적립액 | `emerald-600` | `emerald-400` |
| 보조 텍스트 | `slate-500` | `slate-400` |
| 금액 소수부 · 흐린 텍스트 | `slate-400` | `slate-500` |
| 배지 테두리 | `slate-200` | `slate-700` |

점심 구간은 링을 굵게 덧그어 지우는 방식이라 **배경과 같은 색이어야
한다.** 웹은 여기에 `white` / `slate-950`(`#020617`)을 쓰는데, 다크모드
배경은 `#0a0a0a`라 정확히 같지 않다. 맥에서는 배경색을 그대로 써서 맞춘다.
웹의 이 어긋남은 따로 고칠 거리이고, 고치면 팔레트가 다시 일치한다.

배경과 본문 색은 `app/globals.css`의 CSS 변수에서 그대로 가져온 값이다.
`slate`·`emerald` 값은 Tailwind v4가 oklch로 정의하므로, **빌드된 CSS에서
실제 사용된 색만 뽑아** `shared/golden/palette.json`으로 내보내고
`Palette.swift`를 거기서 생성한다. 손으로 hex를 적지 않는다.

다크모드는 웹의 세 상태 중 "기기 설정을 따른다"만 구현한다. SwiftUI의
`@Environment(\.colorScheme)`로 받는다.

### 5.2 글꼴

| 대상 | 웹 | 맥 |
|---|---|---|
| 금액·시각·상태줄 (`font-mono`) | Geist Mono | Geist Mono (앱에 번들) |
| 그 외 본문 | Arial | Arial |
| 메뉴바 타이틀 | — | 시스템 글꼴 (4.1) |

Geist Mono는 OFL 라이선스라 앱에 번들할 수 있다. 웹은 `next/font/google`로
받아 쓰므로 같은 글꼴이 된다.

본문이 Arial인 것은 `globals.css`의 `body { font-family: Arial, ... }`
때문이다. `--font-geist-sans`를 html에 걸어놓고도 body 선언이 이기고
있어서, **웹에서 실제로 보이는 건 Arial이다.** 디자인을 맞추라는 요구에
따라 맥도 Arial을 쓴다. 웹에서 이 선언을 걷어내 Geist Sans로 바꾸고
싶다면 그건 별도 결정이고, 그때 맥도 같이 바꾼다.

`tabular-nums`는 `NSFont`의 `monospacedDigit` 설정으로 대응한다.

### 5.3 치수

시계는 `components/clock/MinimalFace.tsx`의 `viewBox="0 0 200 200"`
좌표계를 그대로 SwiftUI `Canvas`로 옮긴다.

| 값 | |
|---|---|
| 중심 | `CX`, `CY` (`clock/types.ts`) |
| 진행 링 반지름 | 92 |
| 문자판 반지름 | 76 |
| 링 두께 | 5 |
| 점심 구간 — 지우개 | 9 |
| 점심 구간 — 파선 | 1.5, `dash [2, 3]` |
| 눈금 길이 | 3의 배수는 11, 나머지는 5 |
| 눈금 두께 | 3의 배수는 3, 나머지는 1.5 |
| 시침 | `+10` ~ `-42`, 두께 5 |
| 분침 | `+12` ~ `-62`, 두께 3 |
| 초침 | `+16` ~ `-68`, 두께 1.5 |
| 중심점 | 반지름 3.5 |

선 끝은 전부 `round`다. **바늘 회전에 애니메이션을 걸지 않는다** —
웹과 같은 이유로, 360°에서 0°로 넘어갈 때 역방향으로 한 바퀴 돈다.
매 tick마다 각도를 직접 찍으므로 필요도 없다.

웹은 `html { font-size: clamp(...) }`로 UI 전체를 비례 축소한다. 맥은
팝오버 크기가 고정이므로, 같은 효과를 **기준 글꼴 크기 하나를 정하고
나머지를 그에 대한 배수로 쓰는 것**으로 얻는다. 웹의 Tailwind 단계
(`text-xs` 0.75 / `text-sm` 0.875 / `text-5xl` 3)를 그 배수로 삼는다.

### 5.4 문구

화면에 나오는 한국어는 웹과 글자까지 같게 쓴다: `오늘 벌어들인 금액`,
`세전` / `실수령`, `퇴근까지 HH:MM:SS`, `점심시간 · 재개까지 HH:MM:SS`,
`출근까지 HH:MM:SS`, `오늘 근무 종료`, `· 남은 ₩0`.

금액·시각 포맷도 `lib/format.ts`와 같은 규칙을 따른다. 특히 **금액은
항상 내림한다** — 반올림하면 아직 벌지 않은 1원이 먼저 뜬다.

## 9. 테스트 전략

역할을 섞지 않는다. **정확성은 각자의 유닛 테스트가 보고, 일치성은
골든 파일이 본다.**

### 9.1 골든 파일

```
shared/golden/
  earnings.json      computeEarnings 입력 → 기대 출력
  shift.json         resolveShift
  deductions.json    estimateDeductions
  workdays.json      effectiveWorkDays / isDayOff
  palette.json       웹에서 실제로 쓰는 색 토큰 (5.1)
```

vitest와 Swift Testing이 같은 파일을 읽는다. 규칙이 갈라지는 순간 한쪽
테스트가 실패한다. `palette.json`은 테스트가 아니라 `Palette.swift`
생성에 쓰인다.

**시각은 `[2026, 8, 22, 9, 0, 0]` 배열로 적고 양쪽이 각자 로컬 타임존으로
해석한다.** (월은 0-based) epoch ms를 박으면 "기대값을 하드코딩한 UTC
오프셋으로 만들지 말 것"이라는 기존 제약이 깨진다.

부동소수는 상대 오차 `1e-9`로 비교한다.

### 9.2 골든 생성

손으로 쓰지 않고 **웹 구현에서 뽑아 커밋한다.** 규칙의 단일 출처가
`lib/`이므로, 골든은 "Swift가 `lib/`와 같은 답을 내는가"만 본다.

웹 규칙이 바뀌면 재생성하고, 그때 나오는 diff가 곧 Swift에서 고쳐야 할
목록이 된다.

골든이 웹의 버그를 굳힐 위험은 있다. 그건 웹의 유닛 테스트가 막을 일이지
골든이 할 일이 아니다.

### 9.3 케이스

경계만 촘촘히 깐다.

- 출근 직전 / 직후
- 점심 시작 / 끝
- 퇴근 직후
- 자정 직전 / 직후
- 휴무일 (주말, 공휴일, `dayOverrides`로 지정한 날)
- 월말
- 공휴일 표가 없는 해 (2028)
- 급여 3종 (연봉 / 월급 / 시급)
- 실수령 on / off

### 9.4 기존 웹 테스트

`resolveShift`의 "퇴근 직후 총액 유지" 케이스는 새 규칙에서도 그대로
통과한다. "가장 가까운 시프트"라는 전제에 기대던 케이스는 새 규칙
기준으로 고친다. 3.1 표의 다섯 상황과 휴무일 케이스를 새로 추가한다.

### 9.5 디자인은 테스트하지 않는다

팔레트는 생성으로 맞추고, 치수는 5.3의 표를 보고 옮긴다. 화면이 같은지는
웹과 나란히 띄워 눈으로 본다. 스냅샷 테스트를 두지 않는다 — 두 플랫폼의
렌더링이 픽셀 단위로 같을 수 없어서 거짓 실패만 늘어난다.

## 10. 빌드와 배포

`xcodebuild`로 로컬 빌드해 `/Applications`에 넣는다. **본인 기계에서
빌드한 ad-hoc 서명 앱이라 Gatekeeper가 막지 않는다.** 이슈 #1이 걱정하던
"우클릭으로 열기"나 `xattr -dr com.apple.quarantine`가 필요 없다.

Apple Developer 계정도 GitHub Actions도 필요 없다. 남에게 배포하고
싶어지면 그때 붙인다.

## 11. 저장소 배치

```
SalaryClock/
  app/ components/ hooks/ lib/    웹. 구조 그대로
  shared/golden/                  양쪽이 읽는 기대값과 팔레트
  macos/                          맥 앱
```

한 저장소에 둔다. 이 설계의 유일한 진짜 리스크가 "도메인 규칙이 두 벌"인데,
저장소를 나누면 그 리스크를 키우는 쪽으로 움직인다. 3장의 규칙 변경이
정확히 그 사례다 — TypeScript와 Swift를 같이 고쳐야 하고, 한 커밋에 담기면
한쪽만 고치고 잊기가 구조적으로 어려워진다. 디자인도 마찬가지다.

골든 파일을 공유하려면 저장소가 나뉜 경우 서브모듈이나 패키지 배포가
필요한데, 혼자 쓰는 프로젝트에 그건 과하다.

Next.js 빌드는 `app/` 기준이라 `macos/`가 생겨도 Vercel 배포에 영향이 없다.

**나누는 게 맞아지는 시점:** 맥 앱이 자기 릴리스 주기를 갖거나, 웹을 접고
데스크톱만 가져갈 때. 그때는 `lib/`가 단일 출처일 이유가 사라진다.

## 12. 작업 순서

1. `lib/` 규칙 변경 (3장) + 웹 UI 반영 — 기존 테스트 수정 포함
2. 골든 파일 + 팔레트 추출 스크립트 (9장, 5.1)
3. `SalaryClockCore` 포팅 + 골든으로 검증 (6장)
4. 메뉴바 앱 — `NSStatusItem` + 타이머 (4.1, 4.2)
5. 팝오버 + 시계 얼굴 이식 (4.3, 5.3)
6. 설정 창 (4.4)
7. `/Applications` 설치, 로그인 시 자동 실행 (4.4, 10장)

1번은 그 자체로 웹앱 버그 수정이라 **여기서 멈춰도 이득이 남는다.**
3번까지 끝나면 어려운 부분은 다 끝난 셈이고, 4~7은 평범한 AppKit·SwiftUI
작업이다.
